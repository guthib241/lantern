# Decisions

- Oct 26: OpenAI Python SDK used as the HTTP client because Meta Model API is OpenAI-compatible (per dev.meta.ai quickstart).
- Oct 26: Research findings adopted (see docs/SPEC.md v2): WhatsApp scoped as a personal task/approval console because of WhatsApp's Jan 2026 AI-provider rule, Telegram as fallback; glasses via built-in WhatsApp voice messages, not the glasses SDK; Electron for the overlay; sqlite-vec for local embeddings; Muse Glimmer lane is just an OpenAI-compatible URL so it can be local or self-hosted on Modal.
- Oct 26: User laptop = RTX 4060 Laptop 8 GB VRAM, Ryzen 7, 15.6 GB RAM, 1 TB. Official Glimmer Q4_K_M (~19 GiB) does not fit. Plan: private lane runs Glimmer IQ2_M / IQ2_XXS GGUF (~9-11 GB) in llama.cpp with partial GPU offload, text-only (skip the 1.4 GB vision projector), `-c 8192`, used only for short private tasks (classify, summarise, redact, answer about a private file). Backup: self-hosted Glimmer on Modal. Local embeddings use a small embedding GGUF on CPU. During the demo, close other heavy apps (RAM is tight with Electron + Chromium + model).
- Oct 26 (M2): Paths outside every zone rule are treated as hidden, and the error for a hidden path is the same "outside the folders" message, so the model can't probe for hidden folders. A small set of names (`.ssh`, `.gnupg`, `.aws`, `.env*`, browser login stores, `.lantern`) is always hidden regardless of zones.json. Moving a file needs both source and destination in writable zones (moving changes the source folder too). Without a zones.json, configured roots are writable, so M0 behaviour is unchanged. Private files: the cloud model gets name/type/size/line-or-page count only; content search skips them.
- Oct 26 (M3): Scrubber is our own regex set (no detect-secrets/gitleaks dependency) so it stays small and auditable; card numbers need a Luhn pass and Aadhaar a Verhoeff pass to avoid redacting order numbers. Emails and phone numbers are *not* scrubbed by default because Lantern must address emails and WhatsApp replies; both can be turned on. Scrubbing happens in `GuardedClient` around the OpenAI-compatible client, on `instructions`/`input`/`messages` only; the tool list is never touched so the request prefix stays byte-stable for prompt caching. Audit log is a separate SQLite file (`~/.lantern/audit.db`); the SHA-256 is of the exact scrubbed payload that was sent.
- Oct 26 (M4): Private lane is a tool (`ask_private(path, question)`), not a hidden reroute of the whole conversation: the cloud agent plans, Glimmer reads the private file locally and returns at most a few sentences, which are scrubbed again before going back. If Glimmer is down the tool errors; there is no cloud fallback. Default mode is `fake` (extractive offline answers, badge "Muse Glimmer (fake)") until `LANTERN_GLIMMER_URL` is set. A non-loopback Glimmer URL (Modal) is audited as lane `selfhosted`, shown separately from `local`. Requests use the documented Glimmer sampling (temp 1.0, top_p 0.95, top_k 64) and `reasoning_strength: low` to keep the 8 GB laptop fast.
- Oct 26 (M5): Approvals live in memory (`ApprovalBus`), not SQLite: they expire in 10 minutes anyway and a restart should cancel them. The payload that gets hashed is a compact description of the effect (e.g. path + SHA-256 of the content, from/to for moves), computed twice: once when asking and again right before acting, so a change in between is refused. The CLI keeps a simple y/N prompt (`CallbackGate`) that still goes through the bus; the server will use `BusGate` (agent thread blocks until the desktop or WhatsApp answers). Taint: reading file text or a private-lane answer marks the task tainted; after that `remember`/`forget` (normally automatic) need approval, and every approval card says "[after reading untrusted content]". Taint resets at the start of each task.
- Oct 26 (M6): The server binds only to 127.0.0.1 and every route except `/health` needs a random per-install token stored in `~/.lantern/token` (mode 600), so web pages in the user's browser can't drive Lantern via localhost (CSRF/DNS-rebinding). Tasks run one at a time on a single worker thread; `POST /task` creates the task row first so the caller gets the id immediately. Without `MODEL_API_KEY` the server still starts (UI work), and tasks fail with a clear message. Every websocket step carries a `badge`: model calls say which Meta model ran, tool steps say "on this computer" or the private-lane model.
- Oct 26 (M7): **dev.meta.ai was unreachable from the cloud sandbox** (proxy refused the tunnel), so the computer-use shapes come from Meta's `/docs/computer-use` page as surfaced by web search, plus the cookbook (`03_use_cases/12_computer_use`, `13_macos_cua`). Native protocol (Meta docs): `tools=[{"type":"computer"}]` with no size/environment fields; the model returns `computer_call` with an ordered `actions` list; run them all, send one screenshot back as `computer_call_output` with `output.type="computer_screenshot"`; `pending_safety_checks` (`id`, `code`, `message`) are echoed in `acknowledged_safety_checks` only after the user approves. Function protocol (cookbook): function tools `computer.computer` (0..1000 coordinates) + `computer.stop`, screenshot inside the `function_call_output` content list, `parallel_tool_calls: false`; the API takes at most 50 images per request. The native action field names and coordinate space were not visible, so: the parser accepts both naming styles (`click`/`left_click`, `x,y`/`coordinate`, `keys`/`text`), native defaults to pixel coordinates and function to 0..1000 (override with `LANTERN_CUA_COORDS`), the loop falls back to the function protocol if the API rejects the native tool on the first call, and `python scripts/smoke.py cua` checks both against a calibration page. Re-read the page on the laptop and adjust if it disagrees.
- Oct 26 (M7): Forms are filled DOM-first: one cheap Spark call (`set_values` function tool) maps the goal + profile vault to field values, Playwright fills and reads back ordinary fields, and only what the DOM can't do (custom dropdowns, date pickers) goes to the computer-use model. That keeps Wonder steps (and cost) low and the demo fast. Computer use chains turns with `previous_response_id`; at the 25-step cap that is at most 26 screenshots, under the 50-image limit. Screenshots are 1280x800 JPEG (quality 70) at device scale 1, so screenshot pixels are click pixels.
- Oct 26 (M7): Submit is blocked inside the page by an init script (capture-phase `submit` listener + `form.submit()` override) until Lantern sets the allow flag right before the approved click, so Enter in a field or a model click on "Submit" can't submit. Submit-like clicks end the loop as `submit_requested`. The approval payload is URL + submit button label + SHA-256 of every field value + SHA-256 of all hidden inputs, recomputed after the approval; any difference refuses. The card shows the values; the payload stores only hashes.
- Oct 26 (M7): Hard stops end the computer-use loop instead of retrying: typing into a password/OTP/card/PIN/ID field (checked on the focused element), typing text that looks like a card/ID number, touching a CAPTCHA or payment frame, or navigating off the allowlist. A CAPTCHA anywhere on the page means nothing is submitted ("you do this part"). Sensitive fields are never offered to the planning model at all. URL allowlist: `file://` only inside `demo/forms/`, localhost, and `LANTERN_FORMS_DOMAINS`.
- Oct 26 (M7): Uploads read the file through `policy.read_bytes` and hand Playwright a buffer, so file access still goes through policy.py. Private-zone files are never uploaded by `fill_form` (the user attaches them), keeping "private never leaves the laptop" simple and true.
- Oct 26 (M7): The scrubber now leaves base64 `data:` URLs alone. Regexes can't see pixels, and a PAN- or IBAN-shaped run inside base64 would otherwise corrupt a screenshot mid-run. Bytes and hashes of screenshots are still audited.
- Oct 26 (M7): Known limit: page scripts share the JavaScript world with Lantern's DOM checks, so a hostile page could lie to them. The allowlist, the approval card (which shows the values) and the hard stops on the Python side are the defence; the demo form is our own.
- Oct 26 (M8): developers.facebook.com and core.telegram.org were also unreachable from the sandbox; WhatsApp shapes were confirmed through search results quoting Meta's docs (handshake echoes the raw `hub.challenge`; `X-Hub-Signature-256: sha256=` HMAC-SHA256 of the raw body with the app secret; `interactive.button_reply{id,title}`; up to 3 reply buttons; `GET /{media-id}` then `GET url` with the bearer token, URL valid 5 minutes; free-form messages only inside the 24-hour window). Graph version defaults to `v23.0` (`WHATSAPP_GRAPH_VERSION` to change).
- Oct 26 (M8): Several channels run at once (`LANTERN_CHANNELS=whatsapp,telegram`; default `fake`, a simulated phone the desktop and demo mode can show). The local HTTP API is always on. Approval cards go to every channel; a task's reply goes back to the channel that asked. Owner allowlist in code: messages from anyone else are dropped and counted.
- Oct 26 (M8): Button ids carry the approval id, its nonce and the first 8 hex of its payload hash (`approve:<id>:<nonce>:<hash8>`, 48 bytes, under Telegram's 64-byte limit), so only the card that was shown can answer, and only for the action it showed. The channel itself is trusted after the signature + owner checks. "Show" sends the payload (hashes, not contents).
- Oct 26 (M8): Webhooks verify the signature on the raw bytes, enqueue, and return 200 at once; an inbox thread does the work (voice download, ffmpeg, transcription) and an outbox thread sends, so a slow network never blocks the agent or Meta's webhook timeout. Meta's redeliveries are de-duplicated by message id. Outgoing text is scrubbed and audited (`whatsapp.send` / `telegram.send` show up in "What left my laptop"); voice uploads to Muse Voice Transcribe are audited with their byte count and cost.
- Oct 26 (M8): STOP (any channel, any case, also spoken) is the kill switch: cancel the running task and deny every pending approval. Telegram uses the raw Bot API with long polling over stdlib HTTP, not `python-telegram-bot`, to avoid a dependency. Voice notes are kept in `~/.lantern/media` for now; M15's "forget" will clear them.
- Oct 26 (M8): Scope (WhatsApp's Jan 2026 AI-provider rule): goals from a phone are tagged `[whatsapp]` / `[telegram]` and the agent's rules say to answer chit-chat in one line ("I take tasks here"). `help` explains the scope. WhatsApp is Lantern's personal task and approval console, not a general chatbot.
- Oct 26 (M9): Email uses stdlib `smtplib` (SSL, Gmail app password) and `imaplib`, no Gmail API: no OAuth consent screen to set up before the demo. `verified` means IMAP found our `Message-ID` in the Sent folder (`[Gmail]/Sent Mail` by default), polled with backoff for up to 15 s; providers that don't file SMTP mail into Sent will report `verified: false` honestly. Default mode is `fake` (in-memory Sent folder + `.eml` copies in `~/.lantern/media/outbox`).
- Oct 26 (M9): The send approval is bound to from/to/cc/subject + SHA-256 of the body + name/SHA-256/size of each attachment; attachments are re-read through policy.py right before sending, so editing a file after approval refuses the send. The body is not scrubbed (you approved exact words), but the card warns when it looks like it contains a secret or ID number. Private-zone attachments are allowed only with a PRIVATE warning on the card; hidden files never.
- Oct 26 (M9): Exfiltration guard: addresses seen in untrusted content (file text, private-lane answers, web pages) are tracked per task; a recipient that appears there but not in the user's request or remembered facts gets a ⚠️ line on the card, on top of the usual "[after reading untrusted content]" marker.
- Oct 26 (M10): Desktop logic lives in small pure UMD modules (`desktop/renderer/lib/`: event reducer, expression picker, approval cards, audit view, widget bridge rules), loaded as plain scripts by the renderers and `require`d by `node --test`. No bundler, no ES-module-over-file:// quirks. `npm run mock` starts a dependency-free Node mock of the server (REST + a hand-written WebSocket) that plays the demo story, so the UI can be rehearsed with no Python and no API spend; `tests/test_desktop.py` runs the Node tests inside `python -m pytest`.
- Oct 26 (M10): Widgets render in `widget-host.html` (its own CSP `default-src 'none'; script-src 'unsafe-inline'`) inside a `sandbox="allow-scripts"` iframe, with the widget itself in a nested srcdoc frame that inherits that CSP. This keeps the panel's CSP strict (`script-src 'self'`): a srcdoc frame directly in the panel would inherit the panel's policy and could not run inline widget code. Messages are relayed by `postMessage` and re-checked in the panel (notify, storage.get/set only).
- Oct 26 (M10): **The avatar is Muse's, not ours.** At the user's request, the desktop shows only Muse-made art: `assets/avatar/<expression>.webm` (animated loop from Muse Video / Vibes), `.webp` or `.png` (Muse Image, via `scripts/make_avatar.py` or exported from the MetaMuse app). Until those exist it shows a faceless coloured glow, deliberately not a character.
- Oct 26 (M10): Found and fixed two M6 server bugs while testing the panel against a real uvicorn: (1) `uvicorn` alone has no WebSocket implementation, so `/events` returned 404 outside the test client; `websockets` is now a requirement, and a test runs a real uvicorn and connects. (2) The `/events` handler only noticed a closed window at the next event, leaking its task and sink and hanging shutdown; it now waits on receive and send together.
