# Decisions

- Oct 26: OpenAI Python SDK used as the HTTP client because Meta Model API is OpenAI-compatible (per dev.meta.ai quickstart).
- Oct 26: Research findings adopted (see docs/SPEC.md v2): WhatsApp scoped as a personal task/approval console because of WhatsApp's Jan 2026 AI-provider rule, Telegram as fallback; glasses via built-in WhatsApp voice messages, not the glasses SDK; Electron for the overlay; sqlite-vec for local embeddings; Muse Glimmer lane is just an OpenAI-compatible URL so it can be local or self-hosted on Modal.
- Oct 26: User laptop = RTX 4060 Laptop 8 GB VRAM, Ryzen 7, 15.6 GB RAM, 1 TB. Official Glimmer Q4_K_M (~19 GiB) does not fit. Plan: private lane runs Glimmer IQ2_M / IQ2_XXS GGUF (~9-11 GB) in llama.cpp with partial GPU offload, text-only (skip the 1.4 GB vision projector), `-c 8192`, used only for short private tasks (classify, summarise, redact, answer about a private file). Backup: self-hosted Glimmer on Modal. Local embeddings use a small embedding GGUF on CPU. During the demo, close other heavy apps (RAM is tight with Electron + Chromium + model).
- Oct 26 (M2): Paths outside every zone rule are treated as hidden, and the error for a hidden path is the same "outside the folders" message, so the model can't probe for hidden folders. A small set of names (`.ssh`, `.gnupg`, `.aws`, `.env*`, browser login stores, `.lantern`) is always hidden regardless of zones.json. Moving a file needs both source and destination in writable zones (moving changes the source folder too). Without a zones.json, configured roots are writable, so M0 behaviour is unchanged. Private files: the cloud model gets name/type/size/line-or-page count only; content search skips them.
- Oct 26 (M3): Scrubber is our own regex set (no detect-secrets/gitleaks dependency) so it stays small and auditable; card numbers need a Luhn pass and Aadhaar a Verhoeff pass to avoid redacting order numbers. Emails and phone numbers are *not* scrubbed by default because Lantern must address emails and WhatsApp replies; both can be turned on. Scrubbing happens in `GuardedClient` around the OpenAI-compatible client, on `instructions`/`input`/`messages` only; the tool list is never touched so the request prefix stays byte-stable for prompt caching. Audit log is a separate SQLite file (`~/.lantern/audit.db`); the SHA-256 is of the exact scrubbed payload that was sent.
- Oct 26 (M4): Private lane is a tool (`ask_private(path, question)`), not a hidden reroute of the whole conversation: the cloud agent plans, Glimmer reads the private file locally and returns at most a few sentences, which are scrubbed again before going back. If Glimmer is down the tool errors; there is no cloud fallback. Default mode is `fake` (extractive offline answers, badge "Muse Glimmer (fake)") until `LANTERN_GLIMMER_URL` is set. A non-loopback Glimmer URL (Modal) is audited as lane `selfhosted`, shown separately from `local`. Requests use the documented Glimmer sampling (temp 1.0, top_p 0.95, top_k 64) and `reasoning_strength: low` to keep the 8 GB laptop fast.
- Oct 26 (M5): Approvals live in memory (`ApprovalBus`), not SQLite: they expire in 10 minutes anyway and a restart should cancel them. The payload that gets hashed is a compact description of the effect (e.g. path + SHA-256 of the content, from/to for moves), computed twice: once when asking and again right before acting, so a change in between is refused. The CLI keeps a simple y/N prompt (`CallbackGate`) that still goes through the bus; the server will use `BusGate` (agent thread blocks until the desktop or WhatsApp answers). Taint: reading file text or a private-lane answer marks the task tainted; after that `remember`/`forget` (normally automatic) need approval, and every approval card says "[after reading untrusted content]". Taint resets at the start of each task.
- Oct 26 (M6): The server binds only to 127.0.0.1 and every route except `/health` needs a random per-install token stored in `~/.lantern/token` (mode 600), so web pages in the user's browser can't drive Lantern via localhost (CSRF/DNS-rebinding). Tasks run one at a time on a single worker thread; `POST /task` creates the task row first so the caller gets the id immediately. Without `MODEL_API_KEY` the server still starts (UI work), and tasks fail with a clear message. Every websocket step carries a `badge`: model calls say which Meta model ran, tool steps say "on this computer" or the private-lane model.
- Oct 26 (M7): **dev.meta.ai was unreachable from the cloud sandbox** (proxy refused the tunnel), so the computer-use shapes come from Meta's `/docs/computer-use` page as surfaced by web search, plus the cookbook (`03_use_cases/12_computer_use`, `13_macos_cua`). Native protocol (Meta docs): `tools=[{"type":"computer"}]` with no size/environment fields; the model returns `computer_call` with an ordered `actions` list; run them all, send one screenshot back as `computer_call_output` with `output.type="computer_screenshot"`; `pending_safety_checks` (`id`, `code`, `message`) are echoed in `acknowledged_safety_checks` only after the user approves. Function protocol (cookbook): function tools `computer.computer` (0..1000 coordinates) + `computer.stop`, screenshot inside the `function_call_output` content list, `parallel_tool_calls: false`; the API takes at most 50 images per request. The native action field names and coordinate space were not visible, so: the parser accepts both naming styles (`click`/`left_click`, `x,y`/`coordinate`, `keys`/`text`), native defaults to pixel coordinates and function to 0..1000 (override with `LANTERN_CUA_COORDS`), the loop falls back to the function protocol if the API rejects the native tool on the first call, and `python scripts/smoke.py cua` checks both against a calibration page. Re-read the page on the laptop and adjust if it disagrees.
- Oct 26 (M7): Forms are filled DOM-first: one cheap Spark call (`set_values` function tool) maps the goal + profile vault to field values, Playwright fills and reads back ordinary fields, and only what the DOM can't do (custom dropdowns, date pickers) goes to the computer-use model. That keeps Wonder steps (and cost) low and the demo fast. Computer use chains turns with `previous_response_id`; at the 25-step cap that is at most 26 screenshots, under the 50-image limit. Screenshots are 1280x800 JPEG (quality 70) at device scale 1, so screenshot pixels are click pixels.
- Oct 26 (M7): Submit is blocked inside the page by an init script (capture-phase `submit` listener + `form.submit()` override) until Lantern sets the allow flag right before the approved click, so Enter in a field or a model click on "Submit" can't submit. Submit-like clicks end the loop as `submit_requested`. The approval payload is URL + submit button label + SHA-256 of every field value + SHA-256 of all hidden inputs, recomputed after the approval; any difference refuses. The card shows the values; the payload stores only hashes.
- Oct 26 (M7): Hard stops end the computer-use loop instead of retrying: typing into a password/OTP/card/PIN/ID field (checked on the focused element), typing text that looks like a card/ID number, touching a CAPTCHA or payment frame, or navigating off the allowlist. A CAPTCHA anywhere on the page means nothing is submitted ("you do this part"). Sensitive fields are never offered to the planning model at all. URL allowlist: `file://` only inside `demo/forms/`, localhost, and `LANTERN_FORMS_DOMAINS`.
- Oct 26 (M7): Uploads read the file through `policy.read_bytes` and hand Playwright a buffer, so file access still goes through policy.py. Private-zone files are never uploaded by `fill_form` (the user attaches them), keeping "private never leaves the laptop" simple and true.
- Oct 26 (M7): The scrubber now leaves base64 `data:` URLs alone. Regexes can't see pixels, and a PAN- or IBAN-shaped run inside base64 would otherwise corrupt a screenshot mid-run. Bytes and hashes of screenshots are still audited.
- Oct 26 (M7): Known limit: page scripts share the JavaScript world with Lantern's DOM checks, so a hostile page could lie to them. The allowlist, the approval card (which shows the values) and the hard stops on the Python side are the defence; the demo form is our own.
- Oct 26 (M8): developers.facebook.com and core.telegram.org were also unreachable from the sandbox; WhatsApp shapes were confirmed through search results quoting Meta's docs (handshake echoes the raw `hub.challenge`; `X-Hub-Signature-256: sha256=` HMAC-SHA256 of the raw body with the app secret; `interactive.button_reply{id,title}`; up to 3 reply buttons; `GET /{media-id}` then `GET url` with the bearer token, URL valid 5 minutes; free-form messages only inside the 24-hour window). Graph version defaults to `v23.0` (`WHATSAPP_GRAPH_VERSION` to change).
- Oct 26 (M8): Several channels run at once (`LANTERN_CHANNELS=whatsapp,telegram`; default `fake`, a simulated phone the desktop and demo mode can show). The local HTTP API is always on. Approval cards go to every channel; a task's reply goes back to the channel that asked. Owner allowlist in code: messages from anyone else are dropped and counted.
- Oct 26 (M8): Button ids carry the approval id, its nonce and the first 8 hex of its payload hash (`approve:<id>:<nonce>:<hash8>`, 48 bytes, under Telegram's 64-byte limit), so only the card that was shown can answer, and only for the action it showed. The channel itself is trusted after the signature + owner checks. "Show" sends the payload (hashes, not contents).
- Oct 26 (M8): Webhooks verify the signature on the raw bytes, enqueue, and return 200 at once; an inbox thread does the work (voice download, ffmpeg, transcription) and an outbox thread sends, so a slow network never blocks the agent or Meta's webhook timeout. Meta's redeliveries are de-duplicated by message id. Outgoing text is scrubbed and audited (`whatsapp.send` / `telegram.send` show up in "What left my laptop"); voice uploads to Muse Voice Transcribe are audited with their byte count and cost.
- Oct 26 (M8): STOP (any channel, any case, also spoken) is the kill switch: cancel the running task and deny every pending approval. Telegram uses the raw Bot API with long polling over stdlib HTTP, not `python-telegram-bot`, to avoid a dependency. Voice notes are kept in `~/.lantern/media` for now; M15's "forget" will clear them.
- Oct 26 (M8): Scope (WhatsApp's Jan 2026 AI-provider rule): goals from a phone are tagged `[whatsapp]` / `[telegram]` and the agent's rules say to answer chit-chat in one line ("I take tasks here"). `help` explains the scope. WhatsApp is Lantern's personal task and approval console, not a general chatbot.
- Oct 26 (M9): Email uses stdlib `smtplib` (SSL, Gmail app password) and `imaplib`, no Gmail API: no OAuth consent screen to set up before the demo. `verified` means IMAP found our `Message-ID` in the Sent folder (`[Gmail]/Sent Mail` by default), polled with backoff for up to 15 s; providers that don't file SMTP mail into Sent will report `verified: false` honestly. Default mode is `fake` (in-memory Sent folder + `.eml` copies in `~/.lantern/media/outbox`).
- Oct 26 (M9): The send approval is bound to from/to/cc/subject + SHA-256 of the body + name/SHA-256/size of each attachment; attachments are re-read through policy.py right before sending, so editing a file after approval refuses the send. The body is not scrubbed (you approved exact words), but the card warns when it looks like it contains a secret or ID number. Private-zone attachments are allowed only with a PRIVATE warning on the card; hidden files never.
- Oct 26 (M9): Exfiltration guard: addresses seen in untrusted content (file text, private-lane answers, web pages) are tracked per task; a recipient that appears there but not in the user's request or remembered facts gets a ⚠️ line on the card, on top of the usual "[after reading untrusted content]" marker.
- Oct 26 (M10): Desktop logic lives in small pure UMD modules (`desktop/renderer/lib/`: event reducer, expression picker, approval cards, audit view, widget bridge rules), loaded as plain scripts by the renderers and `require`d by `node --test`. No bundler, no ES-module-over-file:// quirks. `npm run mock` starts a dependency-free Node mock of the server (REST + a hand-written WebSocket) that plays the demo story, so the UI can be rehearsed with no Python and no API spend; `tests/test_desktop.py` runs the Node tests inside `python -m pytest`.
- Oct 26 (M10): Widgets render in `widget-host.html` (its own CSP `default-src 'none'; script-src 'unsafe-inline'`) inside a `sandbox="allow-scripts"` iframe, with the widget itself in a nested srcdoc frame that inherits that CSP. This keeps the panel's CSP strict (`script-src 'self'`): a srcdoc frame directly in the panel would inherit the panel's policy and could not run inline widget code. Messages are relayed by `postMessage` and re-checked in the panel (notify, storage.get/set only).
- Oct 26 (M10): **The avatar is Muse's, not ours.** At the user's request, the desktop shows only Muse-made art: `assets/avatar/<expression>.webm` (animated loop from Muse Video / Vibes), `.webp` or `.png` (Muse Image, via `scripts/make_avatar.py` or exported from the MetaMuse app). Until those exist it shows a faceless coloured glow, deliberately not a character.
- Oct 26 (M10): Found and fixed two M6 server bugs while testing the panel against a real uvicorn: (1) `uvicorn` alone has no WebSocket implementation, so `/events` returned 404 outside the test client; `websockets` is now a requirement, and a test runs a real uvicorn and connects. (2) The `/events` handler only noticed a closed window at the next event, leaking its task and sink and hanging shutdown; it now waits on receive and send together.
- Oct 26 (M11): Lantern's face comes from Muse, two ways. (1) `scripts/make_avatar.py`: Muse Image renders one canonical portrait, then every expression is its own turn with `previous_response_id` = the canonical turn (anchored generation, cookbook `05_muse_image/03_anchored_generation`); branching every expression from the same anchor keeps drift from piling up across a chain. `--canonical your.png` starts from art made in the MetaMuse app (attached once as an `input_image` data URL inside a user message, per cookbook 01). (2) `scripts/import_avatar.py`: images and Vibes / Muse Video clips exported from Meta's apps, videos turned into square silent 360x360 VP9 loops with ffmpeg. dev.meta.ai `/docs/image-generation` and `/docs/file-handling` were unreachable; the cookbook covered every call used, and no Files API upload was needed.
- Oct 26 (M11): Muse Image returns opaque WebP; rather than cutting the background out (fragile, and impossible for video loops), the desktop shows the art as a round glowing portrait. A `manifest.js` (next to `manifest.json`) tells the renderer which file each expression uses, because a `file://` page can't fetch JSON; missing expressions show idle. The repo ships an empty manifest until the user generates or imports the art.
- Oct 26 (M11): Voice output: the listed Meta models include speech-to-text only. Lantern's spoken replies come through the Ray-Ban Meta glasses reading WhatsApp messages aloud. The Muse Realtime Avatar's voice and lip sync live in the MetaMuse app; no API for them was found, so nothing is guessed. If the user shares a doc for a Muse voice API, it gets wired in.
- Oct 26 (M12): Installed packages are read from each venv's `site-packages/*.dist-info` folder names instead of running `<env>/bin/python -m pip list`: same answer, no project code executed just to look, works offline, and it's fast enough to rescan. Conda envs (outside the allowed folders) come from `conda env list --json` / `conda list -p … --json`, cached for an hour. Projects are cached in `~/.lantern/envmap.db`, keyed by the mtimes of their marker files and site-packages folder; a rescan happens at most once a minute and re-reads only changed projects. `policy.walk_dirs` was added so the walk still goes through policy.py (it never descends into dot-folders, node_modules, venvs or hidden zones). Private-zone projects are listed by name only.
- Oct 26 (M12): `run_in_project` allowlist: `pytest` / `python -m pytest` with a few safe flags, `-k EXPR` and paths inside the project; `npm test` (only if package.json has a test script); `pip install <one package spec>` (no options, URLs or VCS). Python always runs from the project's own venv (`.venv`/`venv`/`env`); with no venv, Lantern refuses rather than touch the global Python. No shell. Commands need approval bound to the exact argv and cwd, only run in writable zones, get an environment with API keys, tokens and passwords removed, time out (5 min tests, 10 min pip), and their output comes back as untrusted (taints the task). `pip install` is verified by re-reading the env, not by trusting pip's output.
- Oct 26 (M13): The widget checker is deliberately strict and regex-based (network APIs, code loading, external resources, any URL, host access, raw postMessage, storage APIs, obfuscation like `window[...]`/`.constructor`/`\x` escapes, health-advice phrases, 100 KB). It is only the first layer: a browser test proves that a widget slipping past it still can't fetch, reach the panel or use storage, because of the sandbox + CSP. Generated widgets get one retry with the checker's findings; saved and built-in widgets are re-checked every time they are served, so a file edited on disk is refused. Widget names are slugs (`water-timer`); the user's widgets override built-ins with the same name.
- Oct 26 (M14): Tool search per dev.meta.ai/docs/tool-search (read through search results; the site was unreachable): `{"type": "tool_search"}` in `tools`, `defer_loading: true` on each MCP function, server-side search (`tool_search_call` / `tool_search_output` items before the `function_call`, which the agent ignores and the chain carries). MCP tools are flat functions named `server.tool` (one dot) rather than namespaces, whose exact shape couldn't be read. The tool list order is fixed for prompt caching: Lantern's tools, `finish`, the deferred MCP tools sorted by name, then `tool_search`; with no deferred tool, `tool_search` is never sent. `tool_choice` is never set.
- Oct 26 (M14): MCP servers are other programs: their tool descriptions get hidden text stripped, a "[MCP server 'x', untrusted]" prefix and a length cap (tool-poisoning defence); results are wrapped as untrusted and taint the task; every call needs approval bound to the tool + a hash of its arguments unless the user lists that tool under `read_only` in `~/.lantern/mcp.json`. A server's own read-only hint is not trusted. Sessions stay open in one background asyncio thread; one task owns them all because anyio scopes must be exited by the task that entered them. Uses the MCP Python SDK 2.x (`Client`, `MCPServer`).
- Oct 26 (M14): Lantern's own MCP server (`python -m lantern --mcp`, stdio) exposes read-only tools through the same policy, and forwards `submit_task` / `task_status` to the running Lantern over its token-protected local API, so changes still go through the approval bus (desktop / WhatsApp). Everything it returns is scrubbed and audited as data leaving the laptop (model "mcp" in the audit view).
- Oct 26 (M15): Encryption at rest uses column-level Fernet (`cryptography`), not SQLCipher (painful to install on Windows, and it would replace the stdlib sqlite3). Encrypted: task goals and summaries, step contents (tool arguments, results, replies), fact values, and the audit log's payload previews, stored as `enc1:<token>`. Not encrypted: fact keys (needed for lookups; they are labels like "manager email"), timestamps, model names, token counts, hashes. The key lives in the OS keychain via `keyring` when one works (Windows Credential Locker / macOS Keychain); otherwise in a mode-600 `key` file next to `memory.db`. `LANTERN_KEY_STORE=keyring|file|auto`, and `LANTERN_ENCRYPT=0` turns encryption off. Old plaintext rows are encrypted on first open.
- Oct 26 (M15): Forgetting is real. Both databases run with `PRAGMA secure_delete = ON` (freed pages are zeroed) and `VACUUM` after every forget, so tests can show the bytes are gone from the file. `forget_task` removes the task, its steps, usage and audit rows. "Forget everything" (typed confirmation in the CLI, a confirm dialog on the desktop, a confirm phrase on the API) also overwrites and deletes Lantern's own files: voice notes, screenshots, the email outbox, Lantern's browser profile and the form profile vault. It keeps settings, zones, the key and widgets. That deletion code lives in policy.py (`erase_lantern_data`), which refuses anything outside Lantern's home or inside a user zone.
- Oct 26 (M16): The SAM 3.1 check-in is deliberately narrow. It runs only on a click in the desktop panel: Electron allows the camera for 5 seconds after that click, the panel takes one 640x480 frame and stops the camera immediately, and the image is sent as a data URL and never written to disk. Concepts must be objects. A word list refuses people, faces, body parts, expressions, emotions, moods and health words, so Lantern cannot be asked to look at the user. Request shape and parsing follow cookbook `07_sam/01_api_basics` with Meta's `meta_sam_parser` (SAM License); this parser version finalizes the text lane from `response.content_part.done` itself, so no event rewriting is needed. Only the boxes are used: how many objects and where. The reaction is a fixed, playful line.
- Oct 26 (M17): Retries live in Lantern (`RetryingClient`), not the OpenAI SDK (`max_retries=0`): retries become visible events (the avatar and the CLI say so), every attempt is audited because the retrying client wraps the audited one, and a circuit breaker stops hammering a dead network. Only 408/409/425/429, 5xx, timeouts and connection errors are retried (up to 4 times, 0.5 s doubling to 8 s plus jitter, or the server's `Retry-After` capped at 30 s); 400/401/403/404/422 fail at once with a plain sentence. Failed tasks keep their goal, so "Try again" just queues it as a new task.
- Oct 26 (M17): Rehearsal mode scripts the model and nothing else. `DemoModel` recognises the caller by request shape: the agent (has `finish`), the form planner (`set_values`), computer use (the `computer` tool) or the widget writer (the widget rules). Agent conversations are Python generators keyed by response id, so `previous_response_id` chaining behaves like the real API. The model has no eyes, so the click targets for the custom dropdown are measured once in the same 1280x800 Chromium, the same way the browser tests do. That measurement runs in its own thread because Playwright's sync API can't nest. It reports zero tokens and the audit destination is `rehearsal://nothing-sent`, so the costs and "what left my laptop" views stay honest. Unknown goals get "this is rehearsal mode", never an invented answer.
- Oct 26 (M17): The rehearsal never touches the user's real Lantern data. It uses a new temp folder (or an empty `--demo-dir`): a fixture copy of `demo/home/`, its own zones (Documents writable, Private private), profile vault, memory, audit log and a key *file* (never the OS keychain), and a fake mailer whatever `.env` says. It only borrows `~/.lantern/token`, so the desktop app connects as usual. The fixture copy is the one copy outside policy.py, because these are repo files, not user files. The project venv in `demo/home/Projects/vision-lab/venv/` is named `venv` because `.venv/` is gitignored.
- Oct 26 (M17): Two scrubber fixes the rehearsal surfaced:
  - **JSON tool output:** JSON-looking strings (tool outputs) are decoded and their values scrubbed. Before, `\nAKIA…` in a JSON string had no word boundary before the key, so a key at the start of a line in a file reached the cloud model. The JSON is re-encoded only when something was redacted, so clean payloads stay byte-identical for prompt caching.
  - **Wire ids:** the top-level wire ids of Responses input items are never scrubbed, because a "redacted" `call_id` breaks the chain. Values nested under the same key names (e.g. inside a file's JSON) are still scrubbed.
- Oct 26 (M18): Reminders are a plain timer in code, not a model feature.
  - **Times:** the model turns "at 6" into `when` (it sees Now), and Lantern parses and validates it: ISO 8601, "in N minutes/hours/days" or a clock time; naive times are local, and a clock time already past means tomorrow.
  - **Repeats:** daily or weekly, stepped in local wall-clock time so DST doesn't shift them.
  - **Late delivery:** a reminder that fell due while Lantern was off is delivered at the next start with a note, never silently dropped.
  - **Approval tier:** same as `remember`. Automatic in a trusted task, approval once untrusted content is in context, because a reminder's text goes to the user's phone and must not be plantable by a web page or file.
  - **No advice:** the text is the user's own words; the agent rules say never to add advice.
- Oct 26 (M19): Bulk moves are one tool with one approval rather than N `move_file` cards: nobody reads twenty cards, so one card that shows the grouped plan (and the full list behind "Show") is the safer UX.
  - **Binding:** the approval binds each file's path, size and `mtime_ns`, not a content hash, so tidying big folders stays fast while a file swapped after approval still changes the hash.
  - **Scope:** files only, because a folder move can drag a nested private or hidden zone out of its zone. That gap also existed in `move_file` and is now closed in `policy.move` itself.
  - **Undo:** another `organize_files` with the reversed plan, so it is approved and verified like any change. Lantern still never deletes.
- Oct 26 (M20): Resuming re-runs the goal as a new task instead of replaying the old Responses chain.
  - **Why not replay:** a `previous_response_id` from before a crash may have expired and still holds pending calls whose results we never sent.
  - **What the new task gets:** the old timeline's tool results, summarised ("fill_form (verified); send_email not reached"), with an instruction to check before repeating anything that changes something.
  - **Safety:** every change still needs a fresh approval bound to its payload, so a duplicate submit would show up on a card.
  - **Who marks tasks interrupted:** only the long-running owner, Core (the server) or `--resume`, so a read-only CLI command can never mark a live server's task interrupted. The server refuses to start twice on the same port.
- Oct 26 (M21): The doctor is read-only and offline on purpose.
  - **What it won't do:** it never creates the encryption key (it names the key store it would use), never calls Meta's API (that's `scripts/smoke.py`, which costs money), and probes the private lane only on localhost, since a remote Modal/Baseten URL is the user's business.
  - **Secrets:** shown as present or missing only.
  - **Status levels:** fail = blocks; warn = works but not demo-grade (the stand-in private lane, the simulated phone, the local email outbox, no face yet). Readiness is reported separately for the rehearsal and the real demo, so "what do I still need?" has a one-line answer.
- Oct 26 (M22): Lantern installs in editable mode (`pip install -e .`) because it ships with repo assets: the demo forms, the demo home, built-in widgets and the desktop app. A wheel would need package data and a different asset lookup for no gain during the hackathon. `requirements.txt` stays for people who prefer it. CI uses Python 3.12 on Ubuntu with Playwright's own Chromium (`--with-deps`) and needs no secrets: every test is offline. No LICENSE was added; choosing one is the author's call.
- Oct 26: The Electron e2e runs inside `python -m pytest` whenever `desktop/node_modules` has Electron and Playwright and there is a display or Xvfb; otherwise it skips. It uses Playwright's Electron driver, pinned to the same version as the sandbox's Node Playwright (1.63.0), and never downloads browsers: Electron is the browser. On Linux as root (containers) it adds `--no-sandbox`; on a laptop the app runs with its normal sandbox. The card-number false positive was fixed at its source (our Message-ID) rather than by loosening the card pattern: a scrubber that misses a real card number is worse than one that flags a random id.
- Oct 27 (M23): "Apple design" means following the *language* (calm grouped lists, large titles, materials, system colours, one obvious primary action, motion with restraint), not copying assets.
  - **Fonts and icons:** no SF fonts or SF Symbols are bundled (their licences restrict that) and there are no Apple logos. The font stack uses the system font, which is SF on a Mac and Segoe UI Variable on Windows. Icons are our own 24-pt line drawings.
  - **Colours:** system blue tints actions (white-on-orange fails contrast); the warm amber stays Lantern's brand colour (app icon, glow).
  - **Suggestion chips:** they fill the ask field rather than running at once, so a stray click never starts a paid task.
- Oct 27 (M24): The island may answer an approval only when nothing about it is flagged. Quick Allow needs: no untrusted content in the task, no warnings on the card, not expired. Everything else (every form submit, emails to addresses seen only in files) must be reviewed in the panel, where the whole card is shown. Deny is always available, because saying no is never risky. Any web page counts as untrusted from the moment it opens, not after the tool returns.
- Oct 27 (M25): The Quick Ask hotkey is Ctrl/Cmd+Shift+Space: free by default on macOS, Windows and common Linux desktops. Alt+Space and Ctrl+Space clash with window menus and input sources. If another app holds it, Lantern logs a warning and the menu bar item (M26) still opens Quick Ask. Suggestions that need finishing ("Remind me in 20 minutes to ") go into the field instead of running.
- Oct 27 (M26): Notifications are terse on purpose. An approval says only "Lantern needs your OK: Submit this form?", because notification history and lock screens are visible to anyone nearby and are often synced. The values stay in the app.

- Oct 27 (S3): **the rule, in plain words:**
  - **Cheapest good rung.** The lowest rung that can do this kind of step, with a recent success rate of at least 0.8 (last 20 outcomes).
  - **Optimistic start.** Every rung begins as if it had succeeded 4 times, so a single failure doesn't abandon it (4/5 = 80%) and two do.
  - **Escalate on failure.** A failure moves that kind of step up one rung for the rest of the task. The task's "floor" survives a pause.
  - **De-escalate after success.** After 5 straight successes, the rung below gets one more try.
  - **Within budget.** A rung whose average cost is more than the task has left gives way to a cheaper one.
